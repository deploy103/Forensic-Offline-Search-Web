## 한 줄 결론

HxD는 "오프셋으로 점프해서(Goto) 바이트를 읽고, 선택 구간의 길이를 확인하고, Data Inspector로 리틀엔디언 정수·시간 값을 즉시 해석하는" 세 가지 동작으로 90%를 쓴다. 그리고 **항상 증거물 사본을 열고, 편집은 반드시 덮어쓰기(Overwrite) 모드에서 한다.**

## 어떤 문제에서 필요한가

- 파일이 안 열려서 헤더가 정상인지 눈으로 확인해야 하는 경우 ([FOR-0001](./30sec-triage.html))
- 계산으로 얻은 오프셋(MFT 레코드 위치, 클러스터 위치)에 실제로 무엇이 있는지 봐야 하는 경우
- 8바이트 hex 값이 FILETIME인지 확인하고 시각으로 바꿔야 하는 경우
- 헤더가 지워지거나 바꿔치기된 파일을 **수동으로 되살려야** 하는 경우
- 특정 바이트 패턴이 파일 안 어디에 있는지 찾아야 하는 경우
- CLI가 없는 Windows 환경에서 `xxd`를 대체해야 하는 경우

## 문제에서 처음 볼 단서

1. 파일의 **첫 16바이트** — 형식 판정이 여기서 끝난다
2. 파일의 **마지막 16바이트** — 푸터가 있어야 할 형식이면 조작/절단 여부를 알려준다
3. 파일 크기 — 512/4096의 배수인지, 계산한 구조 크기와 맞는지
4. 화면에 보이는 ASCII 열 — `PK`, `%PDF`, `FILE`, `regf` 같은 문자열이 바로 답이 된다
5. 0x00이 길게 이어지는 구간 — 패딩, slack, 또는 잘려나간 데이터의 경계

## 30초 절차

```text
Ctrl+G -> 오프셋 입력(hex 선택) -> Enter -> Data Inspector 에서 값 확인
```

CLI로 같은 것을 하는 방법을 함께 알아 둔다. 큰 파일에서는 CLI가 훨씬 빠르다.

```powershell
Format-Hex -Path .\target.bin -Count 64
Format-Hex -Path .\target.bin -Offset 5000 -Count 64
```

```bash
xxd -l 64 target.bin              # 앞 64바이트
xxd -s 5000 -l 64 target.bin      # 오프셋 5000 부터 64바이트
tail -c 16 target.bin | xxd       # 마지막 16바이트
```

## 상세 절차

### 1단계 — 무엇을 열 것인가: 파일 / 디스크 / 프로세스 메모리

HxD는 세 종류의 대상을 연다. 이 선택이 "무엇이 보이는가"를 결정한다.

| 열기 대상 | 무엇이 보이나 | 언제 쓰나 |
| --- | --- | --- |
| **파일 열기** | 그 파일의 논리 크기까지만 | 헤더/푸터 확인, 구조 분석, 수동 복구 |
| **디스크 열기 (물리/논리)** | 파티션 테이블, 부트섹터, 메타파일, **비할당·slack 포함 전부** | MBR/GPT 확인, 클러스터 직접 열람 |
| **디스크 이미지 열기** | 위와 같지만 `.dd`/`.raw` 파일 대상 | CTF에서 가장 자주 쓰는 조합 |
| **프로세스 메모리(RAM) 열기** | 실행 중 프로세스의 주소 공간 | 라이브 분석. 평문 문자열·키 탐색 |

핵심 차이: **파일로 열면 slack이나 비할당은 절대 보이지 않는다.** 파일 핸들이 논리 크기까지만 읽기 때문이다. slack을 봐야 한다면 디스크/이미지로 열어 클러스터 오프셋으로 가거나, `icat -s`로 뽑은 파일을 열어야 한다 ([FOR-0034](./file-slack.html)).

이 기능들은 상단 메뉴(도구/Extras 계열 메뉴)에 모여 있다. 관리자 권한이 없으면 물리 디스크 열기가 실패한다.

> 증거물 원본을 직접 열지 않는다. 먼저 사본을 만들고 사본을 연다. HxD는 편집 가능한 에디터이므로 **실수로 한 바이트만 눌러도 원본이 오염된다.**

```powershell
Copy-Item .\evidence.bin .\work.bin
Get-FileHash .\evidence.bin, .\work.bin -Algorithm SHA256
```

두 해시가 같은지 확인한 뒤 `work.bin`을 HxD로 연다. 작업이 끝나면 원본 해시를 다시 확인한다. 물리 디스크는 사본을 만들 수 없으니 **쓰기 방지 장치나 이미지 파일을 쓴다.**

### 2단계 — 오프셋 점프 (Goto, Ctrl+G)

`Ctrl+G`가 이 도구의 심장이다. 대화상자에서 **입력값을 16진수로 볼지 10진수로 볼지 선택**할 수 있고, **기준점**(파일 시작 / 현재 위치 / 파일 끝)도 지정할 수 있다.

| 하고 싶은 것 | 입력 |
| --- | --- |
| 파일 시작 기준 오프셋 0x1388로 이동 | hex 모드, `1388` |
| 파일 시작 기준 5000번째 바이트로 이동 | dec 모드, `5000` (= 0x1388) |
| 현재 위치에서 32바이트 앞으로 | 기준 = 현재 위치, `+20` (hex) 또는 `+32` (dec) |
| 파일 끝에서 16바이트 앞 | 기준 = 파일 끝, `-10` (hex) |

**hex/dec 혼동이 이 도구에서 가장 흔한 실수다.** 계산기로 얻은 값이 10진수인지 16진수인지 확인하고 모드를 맞춘다. 확인하는 방법: 이동한 뒤 하단 상태 표시줄의 오프셋 표기를 본다.

실전에서 자주 쓰는 오프셋 계산:

| 목표 | 계산식 | 예 |
| --- | --- | --- |
| MFT 레코드 위치 | `EntryNumber × 레코드 크기(보통 1024)` | 84213 × 1024 = 86234112 = `0x523D400` ([FOR-0021](./mft-basics.html)) |
| 클러스터의 절대 오프셋 | `파티션시작섹터 × 섹터크기 + 클러스터번호 × 클러스터크기` | 2048 × 512 + 1893 × 4096 = 8802304 = `0x865000` |
| 섹터의 절대 오프셋 | `LBA × 512` | LBA 2048 → 1048576 = `0x100000` ([FOR-0019](./mbr-gpt.html)) |
| slack 시작 지점 | 논리 파일 크기 | 5000 = `0x1388` |

### 3단계 — 검색 (Ctrl+F)

검색 대화상자에서 **무엇으로 찾을지**를 고른다.

| 검색 종류 | 입력 예 | 쓰임 |
| --- | --- | --- |
| **텍스트** | `flag{`, `Users\`, `password` | 문자열 탐색. 인코딩(ANSI / UTF-8 / UTF-16) 선택이 결과를 바꾼다 |
| **hex 값** | `89 50 4E 47`, `FFD8FF`, `504B0304` | 시그니처·구조 탐색 |
| **정수/실수 값** | `1284416` | 특정 수치가 저장된 위치 찾기 (엔디언 선택 주의) |
| **정규식** | `flag\{[^}]+\}` | 지원하는 버전에서만. 검색 종류 목록에 있는지 확인한다 |

검색 옵션에서 반드시 확인할 것:

- **검색 방향** (아래로 / 위로 / 전체) — 커서 위치 뒤만 찾고 "없다"고 결론 내리는 실수가 흔하다
- **대소문자 구분**
- **문자 인코딩** — 한글 문자열은 UTF-16LE로 저장된 경우가 많아 ANSI 검색으로는 안 걸린다
- **모두 찾기** 기능이 있으면 결과 목록으로 받아 개수를 먼저 본다

`F3`으로 다음 결과로 이동한다. 매직 바이트를 hex로 검색하면 파일 안에 숨겨진 다른 파일을 찾을 수 있다. 자주 쓰는 검색 hex:

| 찾는 것 | hex |
| --- | --- |
| PNG 시작 | `89 50 4E 47 0D 0A 1A 0A` |
| PNG 끝(IEND) | `49 45 4E 44 AE 42 60 82` |
| JPEG 시작 | `FF D8 FF` |
| JPEG 끝(EOI) | `FF D9` |
| ZIP 로컬 헤더 | `50 4B 03 04` |
| ZIP EOCD | `50 4B 05 06` |
| PDF 시작 | `25 50 44 46` |
| MFT 레코드 | `46 49 4C 45` (`FILE`) |
| Registry hive | `72 65 67 66` (`regf`) |
| EVTX | `45 6C 66 46 69 6C 65 00` |

전체 파일에 대한 시그니처 스캔은 `binwalk`가 더 빠르다. HxD 검색은 **특정 구조의 위치를 정확히 확인**할 때 쓴다.

### 4단계 — Data Inspector로 값 해석

커서를 어떤 바이트에 놓으면 그 지점부터의 바이트를 여러 자료형으로 동시에 해석해 보여준다. **엔디언 설정(리틀/빅)** 이 표시에 그대로 반영되므로, x86/NTFS 구조를 볼 때는 **리틀엔디언**으로 둔다.

| 자료형 | 바이트 수 | 실전 용도 |
| --- | --- | --- |
| `Int8` / `UInt8` | 1 | 플래그, 카운트 |
| `Int16` / `UInt16` | 2 | 속성 길이, 포트 번호 |
| `Int32` / `UInt32` | 4 | 크기 필드, Unix 시각, USN reason |
| `Int64` / `UInt64` | 8 | **FILETIME**, 파일 크기, USN |
| `Float` / `Double` | 4 / 8 | 드물다 |
| 날짜/시간 계열 | 4 / 8 | FILETIME, time_t, DOS date/time |
| `Binary` | 1 | 비트 단위 플래그 확인 |

**FILETIME 해석이 이 절의 핵심이다.** FILETIME은 1601-01-01 00:00:00 UTC 기준 **100나노초 단위의 8바이트 리틀엔디언 정수**다.

```text
디스크에 보이는 바이트 (리틀엔디언):
  C0 8F E9 57 83 B3 DC 01

빅엔디언으로 뒤집으면:      0x01DCB38357E98FC0
10진수:                     134179465611284416
```

| 변환 | 계산 | 결과 |
| --- | --- | --- |
| 초 단위로 | `134179465611284416 / 10000000` | 13417946561.1284416초 (1601 기준) |
| Unix epoch로 | `13417946561 - 11644473600` | `1773472961` |
| UTC 시각 | — | `2026-03-14 07:22:41.1284416 UTC` |
| **KST 시각** | UTC + 9시간 | **`2026-03-14 16:22:41 KST`** |

Data Inspector에 FILETIME 항목이 없는 버전이라면 8바이트를 `UInt64`로 읽고 아래로 계산한다.

```powershell
# hex -> 시각 (PowerShell)
[datetime]::FromFileTimeUtc(134179465611284416)     # UTC
[datetime]::FromFileTime(134179465611284416)        # 로컬 시간대 적용
```

```python
python3 -c "import datetime;ft=134179465611284416;print(datetime.datetime(1601,1,1)+datetime.timedelta(microseconds=ft/10))"
```

```text
2026-03-14 07:22:41.128442
```

다른 시각 형식도 같은 자리에서 판단한다.

| 형식 | 크기 | 기준 | 단위 |
| --- | --- | --- | --- |
| FILETIME | 8바이트 | 1601-01-01 UTC | 100ns |
| Unix `time_t` | 4 또는 8바이트 | 1970-01-01 UTC | 1초 |
| WebKit/Chrome | 8바이트 | 1601-01-01 UTC | 1마이크로초 |
| DOS date/time | 2+2바이트 | 1980-01-01 (로컬) | 2초 |

FILETIME과 Unix의 차이는 **11644473600초**다. WebKit 값은 FILETIME을 10으로 나눈 스케일이므로, 8바이트 값이 FILETIME치고 10배 작으면 WebKit을 의심한다.

### 5단계 — 선택 구간, 바이트 수, 복사

구조를 셀 때 쓰는 기능들이다.

| 하고 싶은 것 | 방법 |
| --- | --- |
| 특정 구간 선택 | 시작 바이트 클릭 → 끝 바이트에서 `Shift+클릭` |
| 오프셋과 길이로 정확히 선택 | 블록 선택 대화상자(시작/끝 또는 시작/길이 입력) |
| **선택한 바이트 수 확인** | 하단 상태 표시줄의 선택 길이 표기 |
| 현재 커서 오프셋 확인 | 하단 상태 표시줄 |
| 파일 전체 크기 확인 | 하단 상태 표시줄 또는 파일 속성 |
| 선택 구간을 hex 문자열로 복사 | 복사 형식 선택(Copy as) → hex values |
| 선택 구간을 파일로 저장 | 선택 후 "선택 영역 저장" 계열 기능 |
| 값 채우기 | 선택 구간에 특정 바이트 채우기 기능 |
| 두 파일 비교 | 파일 비교 기능(정상 파일과 손상 파일 대조) |
| 체크섬/해시 계산 | 체크섬 계산 기능 (MD5/SHA 등) |

"선택한 바이트 수"는 **구조 크기를 검산하는 유일한 방법**이다. 예: `$STANDARD_INFORMATION`의 크기를 72바이트로 계산했다면, 실제로 그 구간을 선택해 상태 표시줄이 72를 표시하는지 확인한다.

hex 문자열로 복사한 값은 그대로 검색어나 스크립트 입력으로 재사용할 수 있다.

### 6단계 — Insert / Overwrite 모드 (여기서 파일이 망가진다)

HxD는 두 가지 편집 모드를 가지며, `Insert` 키로 전환한다. 현재 모드는 하단 상태 표시줄에 표시된다.

| 모드 | 동작 | 결과 |
| --- | --- | --- |
| **Overwrite (덮어쓰기)** | 입력한 바이트가 그 자리 바이트를 교체 | **파일 크기가 변하지 않는다.** 포렌식 작업의 기본 |
| **Insert (삽입)** | 입력한 바이트가 끼어들고 뒤가 밀린다 | **파일 크기가 늘어나고 이후 모든 오프셋이 어긋난다** |

포렌식에서 Insert 모드는 거의 항상 사고다. 헤더 하나를 고치려다 파일 전체 구조가 밀려 아무것도 안 열리게 된다.

| 상황 | 올바른 모드 |
| --- | --- |
| 손상된 시그니처를 정상 값으로 교체 | Overwrite |
| 잘못된 크기 필드 수정 | Overwrite |
| 앞에 붙은 쓰레기 바이트 제거 | 삭제(선택 후 삭제) 또는 `dd`로 잘라내기 |
| 없어진 헤더를 새로 추가 | Insert 또는 파일 크기 확장 후 Overwrite. **작업 전 사본 필수** |

물리 디스크를 열었을 때는 삽입/삭제가 불가능하다(디스크 크기가 고정이므로). 이 제약은 안전장치이기도 하다.

### 7단계 — 손상된 헤더 수동 복구

`file`이 `data`라고 하고 뷰어가 열지 못하는데 내용은 살아 있는 경우다. 절차는 항상 같다.

```text
1. 사본을 만든다.
2. 앞 32바이트를 본다 -> 무엇이 지워졌는지 판단한다.
3. 파일 안쪽에서 그 형식의 고유 구조를 찾아 형식을 확정한다.
   (PNG 라면 IHDR/IDAT/IEND, JPEG 라면 FF D9, ZIP 이라면 PK 05 06)
4. Overwrite 모드로 정상 시그니처를 써넣는다.
5. 저장 후 file / 뷰어로 검증한다.
```

형식별 복구 값:

| 형식 | 오프셋 0에 써야 하는 바이트 | 확정 근거로 쓸 내부 구조 |
| --- | --- | --- |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `IHDR`(오프셋 12부터), `IDAT`, `IEND` 문자열 |
| JPEG | `FF D8 FF E0` 또는 `FF D8 FF DB` | `JFIF`/`Exif` 문자열, 끝의 `FF D9` |
| GIF | `47 49 46 38 39 61` (`GIF89a`) | 끝의 `3B` |
| PDF | `25 50 44 46 2D 31 2E` (`%PDF-1.`) | `obj`/`endobj`, `%%EOF` |
| ZIP | `50 4B 03 04` | 끝의 `50 4B 05 06`, 내부 파일 이름 문자열 |
| 7z | `37 7A BC AF 27 1C` | — |
| PE | `4D 5A` | `PE\0\0`, `This program cannot be run in DOS mode` |
| SQLite | `53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00` | `CREATE TABLE` 문자열 |

PNG 복구 예:

```text
복구 전 (오프셋 0):
00000000  00 00 00 00 00 00 00 00  00 00 00 0D 49 48 44 52
                                              ^^^^^^^^^^^ "IHDR"

오프셋 8~11 에 00 00 00 0D (=13, IHDR 길이) 와
오프셋 12~15 에 "IHDR" 이 그대로 있다 -> PNG 확정.
지워진 것은 8바이트 시그니처뿐이다.

복구 후:
00000000  89 50 4E 47 0D 0A 1A 0A  00 00 00 0D 49 48 44 52
          ^^^^^^^^^^^^^^^^^^^^^^^  8바이트를 Overwrite 로 써넣는다

검증:
  file fixed.png     -> PNG image data, 1920 x 1080, 8-bit/color RGBA
  pngcheck fixed.png -> OK
```

**IHDR 청크 길이 필드(`00 00 00 0D`)와 `IHDR` 문자열이 오프셋 8과 12에 있다는 사실이 PNG를 확정하는 근거다.** 이 확인 없이 시그니처를 써넣으면 다른 형식을 PNG로 위조하는 셈이 된다.

동일한 논리를 CLI로 처리할 수도 있다.

```bash
# 앞 8바이트만 교체 (원본은 남긴다)
printf '\x89PNG\r\n\x1a\n' > fixed.png
tail -c +9 broken.png >> fixed.png
file fixed.png

# 앞에 붙은 쓰레기 N바이트 제거
dd if=broken.bin of=fixed.bin bs=1 skip=4
```

## 출력 필드 해석

HxD 화면에서 읽어야 하는 것은 네 곳이다.

| 위치 | 표시 | 해석 |
| --- | --- | --- |
| 좌측 열 | 오프셋 (기본 16진수) | 표시 진법을 바꿀 수 있다. 계산 결과와 진법을 맞춰 본다 |
| 중앙 | hex 바이트 | 실제 데이터 |
| 우측 | ASCII 표현 | 인쇄 불가 바이트는 `.`으로 보인다. **`.`이 곧 0x00은 아니다** |
| 하단 상태 표시줄 | 현재 오프셋 / 선택 길이 / 파일 크기 / 편집 모드 | 구조 검산과 사고 방지의 핵심 |
| Data Inspector | 자료형별 해석값 | 엔디언 설정을 확인하고 읽는다 |

우측 ASCII 열에서 판정할 수 있는 것:

| 보이는 패턴 | 해석 |
| --- | --- |
| `PK`, `%PDF`, `FILE`, `regf`, `SQLite format 3` | 형식이 즉시 확정된다 ([FOR-0036](./signature-extension-mismatch.html)) |
| 한 글자마다 `.`이 끼어 있는 문자열 (`f.l.a.g.`) | **UTF-16LE 문자열**. `strings -el`로 뽑아야 한다 |
| 0x00이 길게 이어짐 | 패딩 / slack / 미초기화 영역 |
| 0xFF가 길게 이어짐 | 미사용 플래시, 또는 초기화된 영역 |
| 아무 규칙 없는 고엔트로피 바이트 | 압축 또는 암호화 |

## 흔한 함정

- **증거물 원본을 HxD로 직접 여는 것.** 실수 입력 한 번이 증거를 오염시키고, 저장까지 되면 되돌릴 수 없다. 왜 틀리는가: HxD는 뷰어가 아니라 에디터다. 어떻게: 사본을 만들고 해시로 원본 무결성을 확인한다.
- **Insert 모드로 편집하는 것.** 파일 크기가 변하고 이후 모든 오프셋이 밀려 구조가 전부 깨진다. 하단 상태 표시줄의 모드 표시를 항상 확인하고 Overwrite로 둔다.
- **Goto에서 hex/dec를 혼동하는 것.** 5000(dec)과 5000(hex=20480)은 완전히 다른 위치다. 계산기 결과의 진법을 확인하고 대화상자의 모드를 맞춘다.
- **커서 아래쪽만 검색하고 "없다"고 결론 내리는 것.** 검색 방향이 기본적으로 아래로인 경우가 많다. 파일 처음으로 이동한 뒤 검색하거나 전체 검색 옵션을 쓴다.
- **한글/유니코드 문자열을 ANSI로 검색하는 것.** UTF-16LE로 저장된 문자열은 ANSI 검색에 걸리지 않는다. 인코딩 옵션을 UTF-16으로 바꿔 다시 검색한다.
- **Data Inspector의 엔디언 설정을 확인하지 않는 것.** 같은 8바이트가 빅/리틀에 따라 완전히 다른 수가 된다. NTFS·PE·Windows 구조는 리틀엔디언이다.
- **8바이트 시각 값을 무조건 FILETIME으로 읽는 것.** WebKit(마이크로초)일 수 있다. 결과 연도가 1601 근처거나 수만 년 뒤로 나오면 형식을 잘못 고른 것이다.
- **4 GB 메모리 덤프를 HxD로 열어 훑는 것.** 로딩과 스크롤에 시간을 다 쓴다. 큰 파일은 `xxd -s`/`Format-Hex -Offset`으로 필요한 구간만 보거나 `strings`/`grep -aob`로 위치를 먼저 찾는다.
- **우측 ASCII의 `.`을 0x00으로 단정하는 것.** 인쇄 불가 문자 전부가 `.`으로 표시된다. 실제 값은 중앙 hex 열에서 읽는다.
- **시그니처만 고치고 파일이 정상이라고 결론 내리는 것.** 헤더만 맞고 내부 구조가 손상된 경우가 많다. `file` + 형식별 검사기(pngcheck, `7z t`, exiftool)로 반드시 검증한다.
- **파일 크기를 늘려야 하는 복구에서 크기 확장 없이 오프셋을 쓰는 것.** 파일 끝을 넘는 위치에는 Overwrite로 쓸 수 없다. 크기를 먼저 확장하거나 CLI로 앞부분을 붙인다.
- **물리 디스크를 열었는데 아무 파티션도 안 보인다고 당황하는 것.** 오프셋 0의 MBR/GPT를 먼저 읽고 파티션 시작 LBA를 계산해서 이동한다.

## mini walkthrough

```text
문제:
"복구한 파일이 열리지 않습니다. 사진에 적힌 문자열을 답하세요."
첨부: recovered_0041.png (2.1 MB)

1. 상태 확인
   file recovered_0041.png
   -> recovered_0041.png: data
   뷰어로 열기 실패. pngcheck 도 거부.

2. 첫 시도 (실패한 접근):
   HxD 로 recovered_0041.png 를 열고 오프셋 0 에
   89 50 4E 47 0D 0A 1A 0A 를 입력했다.
   저장 후:
     file recovered_0041.png
     -> PNG image data, 0 x 0, 0-bit
     pngcheck -> "CRC error in chunk IHDR"

   무엇이 틀렸나 (두 가지):
   (a) Insert 모드였다. 8바이트가 '삽입'되어 파일이 2.1 MB + 8 바이트가
       되고 뒤쪽 데이터 전체가 8바이트 밀렸다. 그래서 IHDR 이 깨졌다.
   (b) 원본을 그대로 열어 편집했다. 되돌릴 사본이 없었다.

3. 접근 변경 — 사본부터, 그리고 Overwrite 모드
   Copy-Item .\recovered_0041.png .\work.png
   Get-FileHash .\recovered_0041.png, .\work.png -Algorithm SHA256
   -> (원본이 이미 오염되어 문제 재다운로드. 이후 항상 사본 작업)

   HxD 로 work.png 를 열고 하단 상태 표시줄 확인
   -> 편집 모드: Overwrite  (Insert 였다면 Insert 키로 전환)

4. 무엇이 지워졌는지 먼저 판단
   Ctrl+G -> hex 모드 -> 0 -> Enter

   00000000  00 00 00 00 00 00 00 00  00 00 00 0D 49 48 44 52
   00000010  00 00 07 80 00 00 04 38  08 06 00 00 00 ...

   - 오프셋 8~11 = 00 00 00 0D (=13) : IHDR 청크 길이
   - 오프셋 12~15 = "IHDR"
   - 오프셋 16~19 = 00 00 07 80 = 1920  (너비)
   - 오프셋 20~23 = 00 00 04 38 = 1080  (높이)
   => PNG 확정. 지워진 것은 앞 8바이트 시그니처뿐이다.

   (교차검증: Ctrl+F -> hex 검색 "49 45 4E 44" -> 파일 끝 근처에서
    IEND 발견. PNG 가 맞다.)

5. Overwrite 로 8바이트 써넣기
   오프셋 0 에 커서 -> 89 50 4E 47 0D 0A 1A 0A 입력 -> 저장
   하단 상태 표시줄의 파일 크기가 변하지 않았는지 확인
   -> 2,097,152 그대로 (Overwrite 성공)

6. 검증
   file work.png
   -> PNG image data, 1920 x 1080, 8-bit/color RGBA, non-interlaced
   pngcheck -v work.png
   -> OK: work.png (1920x1080, 32-bit RGB+alpha, non-interlaced)

7. 열어서 확인
   이미지에 문자열이 보인다: flag{h3x_h34d3r_f1x}

8. 부가 확인 — 왜 지워졌나
   Ctrl+G 로 파일 끝 -16 이동 -> IEND 뒤에 아무것도 없음.
   앞 8바이트만 0으로 덮인 형태 = 의도적 은닉 문제였다.

정답: flag{h3x_h34d3r_f1x}
```

2→3단계가 이 글의 요지다. **같은 8바이트를 같은 위치에 썼는데 결과가 달랐다.** 차이는 Insert/Overwrite 모드 하나였고, 그리고 원본을 열었다는 실수 때문에 문제 파일을 다시 받아야 했다. 4단계처럼 **써넣기 전에 오프셋 8~15에서 형식을 먼저 확정하는 절차**를 지키면 잘못된 시그니처를 쓰는 사고도 막을 수 있다.

## 막혔을 때 다음 체크

1. 사본을 열었는가 — 원본 해시가 그대로인지 확인
2. 하단 상태 표시줄의 편집 모드가 **Overwrite**인가
3. Goto의 hex/dec 모드가 입력값의 진법과 맞는가
4. 파일로 열었는가 디스크로 열었는가 — slack/비할당이 필요하면 디스크/이미지로 연다
5. 검색이 파일 전체를 대상으로 했는가 (커서 위치 이후만 본 것이 아닌가)
6. 문자열 검색 인코딩을 UTF-16으로도 시도했는가
7. Data Inspector의 엔디언이 리틀엔디언인가
8. 8바이트 시각이 FILETIME인가 WebKit인가 — 결과 연도로 판별
9. 파일 **끝** 16바이트를 확인했는가 — 푸터로 형식이 확정되는 경우가 많다
10. 헤더를 고친 뒤 형식별 검사기(`pngcheck`, `7z t`, `exiftool`)로 검증했는가
11. 파일이 너무 커서 느린가 → `xxd -s`/`Format-Hex -Offset`으로 구간만 본다
12. 선택 구간의 바이트 수가 계산한 구조 크기와 일치하는가
13. 물리 디스크가 안 열리는가 → 관리자 권한으로 실행했는가
