## 한 줄 결론

카빙은 **최후의 수단**이다. `$MFT`나 `$UsnJrnl`에 레코드가 남아 있으면 `icat`으로 정확한 이름·크기·시각과 함께 꺼내는 것이 항상 먼저이고, 카빙은 그 경로가 막힌 뒤 **비할당 영역에 목표 형식만 좁혀서** 돌린다.

## 어떤 문제에서 필요한가

- 파일시스템 메타데이터가 사라져 `icat`으로 꺼낼 수 없는 경우
- 포맷 후 재사용된 매체 (USB, SD 카드) 에서 이전 데이터를 건져야 하는 경우
- 파일시스템 자체가 인식되지 않는 raw 덤프·메모리 덤프
- 파일 슬랙이나 파티션 사이 미할당 구간에 데이터가 숨겨진 경우
- `icat` 결과가 깨져 나오는 경우 (클러스터 재할당) ([FOR-0042](./tsk-icat.html))

이 글은 **도구 사용법이 아니라 의사결정**을 다룬다. 개별 도구의 옵션은 각 도구 글에서 본다.

## 문제에서 처음 볼 단서

1. `fls -d`에 목표 파일이 **이름째로 나온다** → 카빙하지 않는다. `icat`이 답이다
2. `fls -d` 결과에 `(realloc)` 표시 → 메타데이터가 재사용됨. **카빙 후보**
3. `fls`가 아무것도 못 낸다 / `fsstat`이 파일시스템을 못 읽는다 → **카빙 확정**
4. `mmls -A`의 비할당 구간이 수 GB → 그 구간만 대상으로 삼는다
5. 지문이 "복구된 파일의 개수"나 "이미지 안에 숨은 파일"을 묻는다 → 카빙이 정답 경로
6. 지문이 삭제 **시각**이나 **원래 이름**을 묻는다 → 카빙만으로는 답이 안 나온다. `$MFT`/`$J`가 필요하다

## 30초 절차

```bash
fls -o 2048 -r -p -d image.dd | grep -iE '\.(jpg|png|docx|pdf|zip)$'
```

```bash
# 위에서 목표가 이름째로 나오면 -> 카빙하지 말고 icat
icat -o 2048 -r image.dd 9188 > out.bin && file out.bin

# 안 나오거나 깨지면 -> 비할당만 떼어내 목표 형식만 카빙
blkls -o 2048 image.dd > unalloc.dd
foremost -t jpg,png,pdf -i unalloc.dd -o carved
```

**순서를 바꾸지 않는다.** 이미지 전체에 모든 형식을 카빙하면 몇십 분과 수만 개의 쓰레기를 얻는다.

## 상세 절차

### 1단계 — 결정 트리: 카빙을 쓸지 말지

```text
목표 파일이 있다
  |
  +- fls -d 에 이름이 보인다?
  |     예 -> istat 으로 $DATA 확인
  |            +- Resident            -> icat (거의 항상 성공)
  |            +- Non-Resident, realloc 없음 -> icat -r  -> file 로 검증
  |            +- (realloc) 표시      -> 이름·시각만 채택, 내용은 카빙
  |     아니오
  |
  +- $UsnJrnl($J) 에 레코드가 있다?
  |     예 -> 이름·삭제시각 확보 (내용은 없다) -> 이름을 근거로 카빙 결과 대조
  |     아니오
  |
  +- fsstat 이 파일시스템을 읽는다?
        예   -> blkls 로 비할당만 떼어 카빙
        아니오 -> 이미지 전체를 카빙 (마지막 선택지)
```

| 상황 | 우선 수단 | 이유 |
| --- | --- | --- |
| MFT 레코드 생존 | **`icat`** | 이름·경로·크기·시각이 함께 나온다. 카빙은 이 정보를 전부 버린다 |
| resident 데이터 | **`$MFT` 자체** | 내용이 레코드 안에 있어 볼륨이 없어도 복구된다 ([FOR-0021](./mft-basics.html)) |
| `$J`에 기록 | **`$UsnJrnl` 파싱** | 삭제 시각·원래 이름을 카빙 결과에 붙일 수 있다 ([FOR-0027](./usnjrnl-basics.html)) |
| 레코드 재사용/재할당 | 하이브리드 | 이름·시각은 메타데이터, 내용은 카빙 |
| 파일시스템 파괴 | **카빙** | 다른 수가 없다 |
| 목표가 "개수"나 "숨은 파일" | **카빙** | 메타데이터에 없는 것을 찾는 것이 문제의 의도다 |

**카빙이 버리는 것을 항상 의식한다.**

| 카빙으로 얻는 것 | 카빙으로 얻지 못하는 것 |
| --- | --- |
| 파일 내용(운이 좋으면 온전히) | 원래 파일 이름 |
| 이미지 내 오프셋 | 경로·부모 디렉터리 |
| 형식(시그니처 기준) | MACB 타임스탬프 |
| 대략적인 크기 | 소유자·권한·ADS |

지문이 "삭제 시각"이나 "원래 파일명"을 요구하면 카빙 결과만으로는 답이 성립하지 않는다.

### 2단계 — 카빙 대상 선정

같은 도구라도 **무엇을 입력으로 주는지**가 소요 시간과 결과 품질을 결정한다.

| 대상 | 만드는 방법 | 장점 | 단점 |
| --- | --- | --- | --- |
| **비할당 영역만** | `blkls -o N image.dd > unalloc.dd` (기본 동작이 비할당 블록 복사) | 가장 빠르다. 살아 있는 파일이 결과에 섞이지 않는다 | 오프셋이 원본과 달라진다 → `blkcalc`로 환산 |
| **파일 슬랙만** | `blkls -o N -s image.dd > slack.dd` | 은닉 데이터·이전 파일 잔재 전용 | 조각이 작아 온전한 파일은 드물다 |
| 이미지 전체 | 원본 그대로 입력 | 파티션 밖·테이블 손상 구간까지 포함 | 느리고 살아 있는 파일이 전부 중복으로 나온다 |
| 특정 파티션만 | `dd if=image.dd of=vol.dd bs=512 skip=<Start> count=<Length>` | 범위 한정 | 파티션 밖은 놓친다 |
| 파티션 사이 미할당 | `mmls -A`로 구간 확인 후 `dd`로 절단 | 숨긴 파티션·은닉 영역 | 구간 계산 실수 위험 |
| 볼륨 전체 블록 | `blkls -o N -e image.dd` | 메타데이터 포함 전체 | 이미지 전체와 사실상 같다 |

```bash
# 비할당만 (권장 기본값)
blkls -o 2048 image.dd > unalloc.dd
ls -lh unalloc.dd            # 원본보다 훨씬 작으면 그만큼 시간을 번 것이다

# 슬랙만
blkls -o 2048 -s image.dd > slack.dd
strings -n 8 slack.dd | head -40
```

`blkls` 결과에서 찾은 위치는 **원본 이미지의 위치가 아니다.** `blkcalc`로 되돌린다.

```bash
# blkls 출력의 블록 123456 이 원본 이미지에서 몇 번 블록인가
blkcalc -o 2048 -u 123456 image.dd

# 반대 방향: 원본 이미지의 블록이 비할당 이미지에서 어디인가
blkcalc -o 2048 -d 987654 image.dd

# 슬랙 이미지(blkls -s) 기준 주소를 환산
blkcalc -o 2048 -s 4242 image.dd
```

`-d` / `-s` / `-u` 중 **정확히 하나**를 반드시 준다. 원본 이미지를 인자로 줘야 한다.

이 환산이 필요한 이유는 명확하다. 카빙 결과의 위치를 원본 오프셋으로 되돌려야 `$MFT`의 data run이나 `$UsnJrnl` 레코드와 대조할 수 있다. **"어디에서 나왔는가"를 못 말하면 증거로서의 가치가 떨어진다.**

### 3단계 — 헤더/푸터 기반 vs 구조 기반

| 방식 | 원리 | 성공 조건 | 실패 양상 |
| --- | --- | --- | --- |
| **헤더/푸터 기반** | 시작 시그니처를 찾고 종료 시그니처(또는 최대 크기)까지 잘라낸다 | 파일이 **연속**되어 있고 푸터가 존재한다 | 조각화되면 중간부터 다른 파일 내용. 푸터가 없는 형식은 최대 크기만큼 잘려 거대한 파일이 나온다 |
| **구조 기반** | 형식 내부 구조(길이 필드, chunk, 청크 체인)를 해석해 실제 끝을 판단한다 | 파서가 그 형식을 안다 | 지원하지 않는 형식은 처리 못 한다 |

형식별 성질이다.

| 형식 | 헤더 | 푸터/끝 판정 | 카빙 난이도 |
| --- | --- | --- | --- |
| JPEG | `FF D8 FF` | `FF D9` | 낮음 (헤더/푸터 모두 있다) |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `IEND` + CRC | 낮음 |
| GIF | `GIF87a` / `GIF89a` | `00 3B` | 낮음 |
| PDF | `%PDF-` | `%%EOF` | 중간 (`%%EOF`가 여러 번 나온다) |
| ZIP / docx / xlsx / apk | `50 4B 03 04` | EOCD (`50 4B 05 06`) | 중간 (구조 해석이 유리) |
| PE (exe/dll) | `4D 5A` | **없음** | 높음 (헤더의 크기 필드 해석 필요) |
| SQLite | `SQLite format 3\0` | 없음 | 높음 (페이지 크기·개수 해석) |
| 텍스트/로그 | 없음 | 없음 | **카빙 불가.** 문자열 검색으로 접근한다 |

매직 바이트 대조는 [FOR-0001](./30sec-triage.html)에서 정리한다.

**푸터가 없는 형식을 헤더 기반으로 카빙하면 반드시 크기가 부풀려진다.** 결과의 크기 분포가 특정 값(도구의 최대 크기 설정)에 몰려 있으면 그 형식은 전부 잘린 것이다.

### 4단계 — 조각화(fragmentation) 때문에 카빙이 실패하는 원리

헤더/푸터 카빙은 **파일이 디스크에 연속 배치되어 있다**는 가정 위에서 동작한다. 이 가정이 깨지면 결과가 조용히 오염된다.

```text
[정상: 연속 배치]
  클러스터  100  101  102  103  104
  내용     [A1][A2][A3][A4][A5]        <- 카빙 성공

[조각화]
  클러스터  100  101  102  103  104
  내용     [A1][A2][B1][B2][A3]        <- A 의 3번째 조각이 멀리 있다
  카빙 결과: A1 A2 B1 B2 A3 ... 를 한 파일로 붙인다
             앞부분만 정상, 중간부터 다른 파일 내용
```

| 조각화가 생기는 원인 | 결과 |
| --- | --- |
| 디스크 여유 공간이 적을 때 쓰기 | 빈 구멍에 나눠 담긴다 |
| 파일을 여러 번 이어 쓰기(append) | 뒤쪽 조각이 다른 위치로 |
| 삭제·생성 반복 | 자유 공간이 파편화 |
| 큰 파일 (수 MB 이상) | 통째로 들어갈 연속 공간이 없다 |

**증상별 판정**이 실전에서 중요하다.

| 카빙 결과 증상 | 원인 추정 |
| --- | --- |
| JPEG가 위쪽 절반만 정상이고 아래가 회색/노이즈 | 조각화. 중간부터 다른 데이터 |
| ZIP이 `unzip -t`에서 CRC 오류 | 조각화 또는 일부 클러스터 재할당 |
| PDF가 열리지만 페이지 일부만 | 조각화 |
| 크기가 도구 최대치에 딱 맞다 | 푸터를 못 찾아 잘렸다 |
| `file`이 `data`라고 한다 | 헤더 오탐(다른 파일 안의 우연한 시그니처) |
| 파일이 정상인데 내용이 다른 파일 | 헤더 위치는 맞고 데이터가 이미 덮였다 |

조각화된 파일은 헤더/푸터 카빙으로 복원할 수 없다. 이 경우의 선택지다.

| 선택지 | 방법 |
| --- | --- |
| 구조 기반 파서에 맡긴다 | 형식 내부 구조를 아는 도구로 재시도 |
| 메타데이터로 돌아간다 | `$MFT` data run으로 조각 위치를 직접 읽어 `dd`로 이어 붙인다 |
| 앞부분만 활용 | 플래그가 파일 앞쪽 텍스트/메타데이터에 있으면 조각 하나로 충분하다 |
| 문자열로 우회 | 이미지에 직접 `strings`/`grep -a`로 목표 문자열 검색 |

```bash
# 파일 복구가 아니라 문자열이 목표라면 카빙을 건너뛴다
grep -abo 'flag{' image.dd | head
strings -a -t d -n 8 unalloc.dd | grep -i 'flag'
```

**"파일을 복구해야 한다"와 "안에 있는 문자열을 찾아야 한다"는 다른 문제다.** 후자면 카빙은 우회로일 뿐 필수가 아니다.

### 5단계 — 클러스터 정렬 가정

파일시스템은 파일을 **클러스터 경계**에 배치한다. 따라서 삭제된 파일의 헤더는 거의 항상 클러스터 시작에 있다.

```bash
fsstat -o 2048 image.dd | grep -E 'Sector Size|Cluster Size'
# Sector Size: 512
# Cluster Size: 4096
```

| 정렬 가정 | 효과 | 위험 |
| --- | --- | --- |
| 클러스터 경계만 검사 | 스캔 대상이 1/4096로 줄어 **매우 빠르다** | 임베디드 파일(문서 안의 이미지, ZIP 내부)을 놓친다 |
| 섹터 경계만 검사 | 빠르고 대부분의 실제 파일을 잡는다 | 임베디드는 여전히 놓친다 |
| 전 바이트 검사 | 임베디드까지 다 찾는다 | 느리고 오탐이 폭증한다 |

| 목표 | 권장 정렬 |
| --- | --- |
| 삭제된 사용자 파일 복구 | **클러스터 정렬** |
| 파일 안에 숨긴 파일(스테가노·연결) | **전 바이트** — 이때는 카빙 도구보다 `binwalk`가 맞다 |
| 슬랙의 잔재 | 정렬 무의미 (조각이므로 전 바이트) |
| 메모리 덤프 | 전 바이트 (페이지 정렬을 기대할 수 없다) |

정렬 옵션 이름은 도구마다 다르다. 각 도구 글에서 확인한다.

### 6단계 — 목표 형식을 좁혀 시간을 줄인다

이것이 카빙 시간을 줄이는 **가장 효과적인 단 하나의 조치**다.

| 지문의 표현 | 좁힐 형식 |
| --- | --- |
| "사진", "이미지" | `jpg,png,gif` |
| "문서" | `pdf,doc,docx,xls,xlsx` (docx/xlsx는 ZIP으로도 걸린다) |
| "압축 파일" | `zip,rar,7z,gz` |
| "실행 파일" | `exe,dll` |
| "동영상" | `mp4,avi,mov` |
| 형식 언급 없음 | **먼저 `strings`/`grep`로 정찰**한 뒤 결정 |

형식을 모를 때는 카빙 전에 어떤 시그니처가 얼마나 있는지 센다.

```bash
# 어떤 형식이 실제로 있는지 개수를 먼저 센다
for sig in $'\xff\xd8\xff' $'\x89PNG' '%PDF' 'PK\x03\x04'; do
  printf '%-10s ' "$sig"
  grep -c -a -F "$(printf "$sig")" unalloc.dd
done

# 또는 오프셋과 함께
grep -abo -F "$(printf '\xff\xd8\xff')" unalloc.dd | wc -l
```

개수가 0인 형식을 카빙 목록에 넣는 것은 순수한 시간 낭비다.

시간 예산 감각이다.

| 입력 | 형식 범위 | 대략적 소요 |
| --- | --- | --- |
| `blkls` 비할당 (수 GB) | 3~5개 형식 | 분 단위 |
| `blkls` 비할당 (수 GB) | 전 형식 | 수십 분 |
| 이미지 전체 (수백 GB) | 전 형식 | 시간 단위 — **대회장에서 선택하지 않는다** |

### 7단계 — 도구 선택 기준

| 도구 | 방식 | 강점 | 약점 | 언제 고르나 |
| --- | --- | --- | --- | --- |
| **foremost** | 헤더/푸터 + 설정 파일 | 형식을 `-t`로 좁히기 쉽다. 감사 로그(`audit.txt`)에 오프셋이 남는다 | 조각화에 약하다. 기본 지원 형식이 제한적 | 형식이 정해진 표준 카빙의 **1차 선택** |
| **scalpel** | 헤더/푸터 (설정 파일 필수) | 설정 파일에 형식·최대 크기를 세밀히 지정. 클러스터 정렬 옵션 | 설정 파일을 편집해야 동작한다. 조각화에 약하다 | 커스텀 시그니처가 필요할 때 |
| **photorec** | 형식별 내부 구조 인식 | **회수율이 가장 높다.** 200개 이상 형식. 비할당만/파티션 전체 선택 가능 | TUI 대화형. 원래 이름·경로 없음 | "최대한 많이 건져라" 문제 |
| **binwalk** | 전 바이트 시그니처 스캔 + 추출 | **파일 안에 붙은/숨긴 파일**을 찾는 데 최적. 엔트로피 분석 | 디스크 이미지 대상으로는 오탐이 많다 | 단일 파일 안의 은닉, 펌웨어 |
| **bulk_extractor** | 특징(feature) 추출 | 이메일·URL·전화번호 등 **문자열 특징**을 대량 추출 | 파일 복구 도구가 아니다 | "어떤 계정/도메인이 등장했나" |
| **Autopsy (PhotoRec Carver)** | GUI 통합 | 결과가 케이스 트리(`$CarvedFiles`)에 들어와 다른 artifact와 함께 본다 | 매우 느리다 | 이미 Autopsy로 작업 중일 때 ([FOR-0018](./autopsy-ingest.html)) |
| **Sleuth Kit (`icat`/`blkls`/`blkcalc`)** | 메타데이터 기반 | **카빙이 아니다.** 정확한 파일을 정확히 꺼낸다 | 메타데이터가 있어야 한다 | **항상 먼저 시도** ([FOR-0042](./tsk-icat.html)) |

선택 순서는 이렇다.

```text
1. icat            (메타데이터 생존)
2. foremost -t     (형식 확정, 빠른 1차)
3. photorec        (회수율 우선, 형식 불확실)
4. binwalk         (파일 안의 파일)
5. bulk_extractor  (문자열 특징이 목표)
```

### 8단계 — 결과 검증

**카빙 결과는 기본적으로 신뢰하지 않는다.** 다음 네 단계를 전부 통과한 것만 답으로 쓴다.

```bash
cd carved

# 1) 형식 판정 — 헤더 오탐 걸러내기
find . -type f -exec file {} + | grep -v -iE 'JPEG|PNG|PDF|Zip' 

# 2) 크기 이상치 — 0바이트와 최대치에 몰린 것
find . -type f -printf '%s %p\n' | sort -n | head -20     # 너무 작다
find . -type f -printf '%s %p\n' | sort -nr | head -20    # 최대치에 붙어 있다

# 3) 실제로 열리는가 (형식별 구조 검사)
for f in *.zip;  do echo "== $f"; unzip -t "$f" >/dev/null 2>&1 && echo OK || echo BAD; done
for f in *.png;  do pngcheck "$f"; done
for f in *.jpg;  do exiftool -q -q "$f" >/dev/null 2>&1 && echo "OK $f" || echo "BAD $f"; done

# 4) 해시 — 문제에서 준 해시 또는 $MFT 대조용
find . -type f -exec md5sum {} + > carved.md5
```

| 검증 항목 | 통과 기준 | 실패 시 |
| --- | --- | --- |
| `file` 판정 | 기대한 형식 이름 | 헤더 오탐. 버린다 |
| 크기 0 또는 수백 바이트 | 형식의 최소 크기 이상 | 헤더만 걸린 조각 |
| 크기가 도구 최대치와 동일 | 그보다 작아야 정상 | 푸터 못 찾음. 잘렸다 |
| 구조 검사(`unzip -t`, `pngcheck`) | 오류 없음 | 조각화. 복원 불가 |
| 실제 열어 보기 | 내용이 온전 | 아래쪽 손상 = 조각화 |
| 해시 대조 | `$MFT`/문제 제시 해시와 일치 | 부분 복구 |

**눈으로 열어 보는 것을 생략하지 않는다.** JPEG는 위 절반만 정상인 경우가 흔하고, `file`은 그것을 정상으로 판정한다.

### 9단계 — 중복 결과 정리

이미지 전체를 카빙하거나 여러 도구를 돌리면 같은 파일이 여러 번 나온다.

```bash
# 1) 완전 동일 파일 제거 (해시 기준)
find carved -type f -exec md5sum {} + | sort | awk '
  { if ($1 == prev) print $2; else prev=$1 }' > dup.txt
wc -l dup.txt
# 확인 후 삭제
# xargs -a dup.txt rm -f

# 2) 해시별 개수 — 어떤 파일이 몇 번 나왔나
find carved -type f -exec md5sum {} + | awk '{print $1}' | sort | uniq -c | sort -nr | head

# 3) 형식·크기별 분포로 노이즈 덩어리 파악
find carved -type f -exec file -b {} + | cut -d, -f1 | sort | uniq -c | sort -nr
```

| 중복의 유형 | 원인 | 처리 |
| --- | --- | --- |
| 해시가 완전히 같다 | 이미지 전체 카빙 시 할당 파일과 비할당 사본 | 하나만 남긴다 |
| 앞부분만 같고 크기가 다르다 | 푸터 판정 차이 (같은 헤더, 다른 종료점) | **큰 쪽이 아니라 구조 검사를 통과한 쪽**을 남긴다 |
| 같은 이미지의 썸네일과 원본 | EXIF 썸네일이 별도 JPEG로 카빙됨 | 크기로 구분 |
| 여러 도구의 결과 | 도구별 판정 차이 | 해시로 합집합을 만든 뒤 중복 제거 |

썸네일은 버리지 말고 확인한다. 원본이 조각화로 깨져도 **EXIF 썸네일이 온전해 답이 보이는 경우**가 있다.

## 흔한 함정

- **`fls`를 돌려 보지 않고 바로 카빙하는 것.** `$MFT`에 레코드가 남아 있으면 `icat`이 이름·시각까지 준다. **가장 비싼 실수이며, 카빙에 30분을 쓴 뒤에야 알게 된다.**
- **이미지 전체를 대상으로 모든 형식을 카빙하는 것.** 살아 있는 파일이 전부 중복으로 나오고 시간이 폭발한다. → `blkls`로 비할당만 떼고 `-t`로 형식을 좁힌다.
- **카빙 결과의 파일명을 원래 이름으로 답하는 것.** 오프셋에서 생성된 이름이다. 원래 이름은 `$MFT`/`$J`에서만 나온다.
- **카빙 결과에 타임스탬프가 있다고 믿는 것.** 파일시스템 시각은 없다. 있는 것은 EXIF나 문서 내부 메타데이터뿐이며 그것은 파일시스템 시각과 다른 값이다.
- **`file`이 형식을 맞췄다고 복구 성공으로 판정하는 것.** 헤더만 맞아도 그렇게 나온다. 반드시 구조 검사(`unzip -t`, `pngcheck`)와 실제 열기까지 한다.
- **크기가 최대치에 몰린 결과를 그대로 제출하는 것.** 푸터를 못 찾아 잘린 것이다. 형식별 최대 크기 설정을 조정해 재시도한다.
- **조각화된 파일을 옵션으로 해결하려 하는 것.** 헤더/푸터 카빙에는 조각을 이을 정보가 없다. `$MFT` data run으로 돌아가거나 앞부분만 활용한다.
- **`blkls` 결과의 오프셋을 원본 이미지 오프셋으로 쓰는 것.** 다른 좌표계다. `blkcalc -u`로 환산해야 다른 artifact와 대조할 수 있다.
- **`blkcalc`에 `-d`/`-s`/`-u`를 두 개 이상 주거나 하나도 안 주는 것.** 정확히 하나가 필수다. 그리고 인자로 주는 이미지는 **원본**이어야 한다.
- **중복 제거를 안 해 결과 개수를 답으로 쓰는 것.** "복구된 파일 개수"를 묻는 문제에서 중복과 헤더 오탐을 세면 틀린다. → 해시 중복 제거 + `file` 검증 후에 센다.
- **`binwalk`를 디스크 이미지에 돌리는 것.** 전 바이트 스캔이라 오탐이 쏟아진다. `binwalk`는 **단일 파일 안의 은닉**을 볼 때 쓴다.
- **`bulk_extractor`를 파일 복구 도구로 쓰는 것.** 문자열 특징 추출 도구다. 파일을 복원하지 않는다.
- **텍스트/로그를 카빙하려 하는 것.** 시그니처가 없어 카빙 대상이 아니다. `grep -abo` / `strings`로 직접 찾는다.
- **슬랙을 무시하는 것.** 작은 은닉 데이터와 이전 파일의 잔재가 여기 남는다. `blkls -s`는 몇 초면 끝난다.
- **클러스터 크기를 확인하지 않고 정렬 옵션을 쓰는 것.** `fsstat`의 `Cluster Size`가 근거다 ([FOR-0043](./tsk-fsstat.html)).

## 교차검증

```bash
# 1) 카빙 개수 vs 메타데이터 기준 삭제 파일 개수

find carved -type f -name '*.jpg' -exec file -b {} + | grep -c JPEG

# 2) 카빙 결과가 살아 있는 파일의 중복인지 확인
#    (할당 파일의 해시 목록을 만들어 대조)
find /mnt/case -type f -name '*.jpg' -exec md5sum {} + | awk '{print $1}' | sort -u > alive.md5

blkcalc -o 2048 -u 123456 image.dd

# 4) 두 도구의 결과를 합집합으로 비교
find carved_foremost -type f -exec md5sum {} + | awk '{print $1}' | sort -u > a.md5
find carved_photorec -type f -exec md5sum {} + | awk '{print $1}' | sort -u > b.md5

comm -23 a.md5 b.md5 | wc -l               # foremost 만 찾은 것

# 5) 문자열 기준 최종 확인 — 답이 이미지에 그대로 있는지

```

두 도구의 결과가 크게 다르면 방식 차이(헤더/푸터 vs 구조 기반) 때문이다. **회수율이 낮은 쪽을 버리지 말고 양쪽 합집합을 검증 대상으로 삼는다.**

1단계와 4단계를 비교한다. **같은 도구로 38분에 31만 개 vs 1분 40초에 51개.** 차이는 도구가 아니라 세 가지 결정이었다.

| 결정 | 1단계(실패) | 4단계(성공) |
| --- | --- | --- |

그리고 6단계가 마지막 교훈이다. **`file`이 `JPEG`라고 답한 44개 중 실제로 온전한 것은 소수였다.** 눈으로 열어 보는 단계를 생략하면 답을 지나친다.

## 막혔을 때 다음 체크

1. `fls -o N -r -p -d`를 먼저 돌렸는가 — 목표가 이름째로 나오지 않는가
2. `istat`으로 `$DATA`가 resident인지 확인했는가 (resident면 `$MFT`만으로 복구된다)
3. `(realloc)` 표시를 확인했는가
4. `$UsnJrnl:$J`를 파싱해 삭제 시각·원래 이름을 확보했는가
5. `blkls`로 **비할당만** 떼어냈는가 — 입력 크기가 실제로 줄었는가
6. 슬랙(`blkls -s`)도 확인했는가
7. 목표 형식을 좁혔는가 — 그 형식의 시그니처가 실제로 존재하는지 개수를 셌는가
8. `fsstat`의 `Cluster Size`를 확인하고 정렬 가정을 세웠는가
9. 결과에서 `file` 판정이 `data`인 것을 버렸는가
10. 크기가 도구 최대치에 몰린 것을 "잘림"으로 판정했는가
11. 해시로 중복을 제거했는가
12. 구조 검사(`unzip -t`, `pngcheck`, `exiftool`)를 통과했는가
13. **실제로 열어 봤는가** — 위 절반만 정상인 파일을 성공으로 세지 않았는가
14. EXIF 썸네일이 별도로 카빙되지 않았는가 (원본이 깨졌어도 썸네일이 답일 수 있다)
15. 조각화가 확실하면 `$MFT` data run으로 조각을 직접 이어 붙일 수 있는가
16. 애초에 필요한 것이 파일이 아니라 문자열인가 → `grep -abo` / `strings -a -t d`
17. 카빙 위치를 `blkcalc -u`로 원본 오프셋으로 환산했는가
18. 회수율이 부족하면 구조 기반 도구로 다시 돌렸는가
